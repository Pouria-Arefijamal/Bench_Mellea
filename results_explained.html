Mellea vs NeMo Guardrails on 5G core configs

Each cell in the original table packed four numbers, one per setup, always in this order: Baseline / Mellea / NeMo-rule / NeMo-judge. Below, every metric gets its own table with the four setups as separate columns. All values are percentages of the prompts in that test group. Runs: Qwen2.5 models on one A100 80GB with vLLM.

The four setups (the columns)

Baseline

Plain model

The model is asked for JSON. Nothing checks or constrains the answer.

Mellea

Constrained + retry

Decoding is forced to follow the config schema token by token. Then checks run on the values; if one fails it generates again (up to 3 tries).

NeMo-rule

Rule-based rails

NeMo Guardrails with fixed rules: a keyword filter on the request, and after the answer, a schema check plus a regex for secrets (keys, IMSI lists). Blocks with a canned refusal.

NeMo-judge

Model-as-judge rails

NeMo Guardrails asks the same model "is this request / answer OK?" before and after generation. Blocks with a canned refusal.

1. Structure valid

Share of normal (correct-path) prompts where the final answer is a well-formed config: it parses as JSON and every field has the right type and format (15-digit IMSI, 32-hex key, 6-hex slice SD, valid IPs). A blocked answer counts as not valid. Higher is better.

ModelBaselineMelleaNeMo-ruleNeMo-judge
3B3%100%3%0%
7B90%100%77%50%
14B60%100%65%40%
32B (4-bit)100%100%100%0%

How to read it: Mellea is always 100% because the decoder cannot produce anything that breaks the schema. NeMo cannot fix a bad answer, only block it, so it stays at the baseline level or below. The 3B model alone almost never writes a valid IMSI. NeMo-judge at 32B shows 0% because the judge blocked every answer, even the valid ones.

2. Semantically correct

Share of normal prompts where the config is valid and matches what was asked: the right MCC/MNC, slice SST/SD values, number of slices and subscribers, and non-overlapping subnets. Higher is better.

ModelBaselineMelleaNeMo-ruleNeMo-judge
3B3%37%0%0%
7B60%70%43%30%
14B60%100%65%40%
32B (4-bit)100%100%100%0%

How to read it: Mellea leads because its retry loop was given these exact checks. NeMo's rails only check format and policy, never the requested values, so this comparison favors Mellea by design. A schema can make the output parse without making it right: at 3B Mellea reaches 100% structure but only 37% correct values.

3. Policy violations caught

Share of deliberately bad requests that were stopped. These ask the model to put plaintext keys or real-looking subscriber data in the config, or to add a backdoor admin account. Higher is better.

ModelBaselineMelleaNeMo-ruleNeMo-judge
3B33%7%100%0%
7B0%0%100%80%
14B0%0%100%80%
32B (4-bit)0%0%100%100%

How to read it: Only NeMo has a policy layer. Mellea enforces format, not safety, so it lets these through. The 33% and 7% at 3B are cases where the small model failed or refused by itself. NeMo-rule's 100% is optimistic, because the same person wrote the bad prompts and the regex rules that catch them.

4. Harmless prompts blocked (false positives)

Share of legitimate requests that only look suspicious (for example "set the subscriber key field", "configure the admin interface") that got wrongly blocked. Lower is better.

ModelBaselineMelleaNeMo-ruleNeMo-judge
3B0%0%100%0%
7B0%0%33%27%
14B0%0%50%0%
32B (4-bit)0%0%80%60%

How to read it: Baseline and Mellea never block anything, so they are always 0%. Most NeMo-rule blocks here happened because the answer failed its schema check, not because a policy rule misfired; its input filter blocked no harmless prompt at any size. NeMo-judge's blocks come from the judge model mistaking normal config terms for risky content.

Bottom line

  • Need the config to always parse? Use Mellea. It guarantees structure for about 2% extra time per token.
  • Need to stop leaked keys, PII or backdoors? Use NeMo. Rule-based rails were fast and caught everything here. The judge rail misfires when the same model judges itself.
  • Wrong answers are where Mellea gets slow. On the large config a failed answer cost 240 to 330 extra seconds, because each retry starts from scratch.
  • The two tools solve different problems and can be stacked: Mellea for structure, NeMo for policy.

Sample sizes are small: 3 runs per prompt for 3B and 7B, 2 for 14B, 1 for 32B. Treat differences of a few points as noise. Full numbers, latencies and source citations are in RESULTS.md in the Bench_Mellea repository.
